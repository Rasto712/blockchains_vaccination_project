# Validation and evidence

Status (2026-09-28): every check below has been run on the implemented code. The commands are in the [README](../README.md). The Solidity, gas, timing and Python check results are in evaluation/results/; `python -m evaluation.export_python_results` writes the PY rows to evaluation/results/test_results.csv.

Three Solidity suites exist under test/, named after their contracts, with 38 tests (IDs SOL-IR-01..09, SOL-CM-01..22, SOL-RT-01..07; catalogue in docs/FROM_DEV_2.md). They run against the real contracts, and all 38 pass against the implemented IdentityRegistry, ConsentManager and ConsentRewardToken (`npm test`, which is `npx hardhat test solidity`: 38 passing, 0 failing). `python -m evaluation.export_solidity_results` runs that command, saves the raw log to evaluation/results/solidity_test_run.log and writes the observed results to evaluation/results/solidity_test_results.csv (SOL rows only). A test blocked by a failing setUp() is recorded as fail, a missing row means not run, and the exporter refuses to write a CSV whose counts disagree with Hardhat's summary. Re-run it after any contract change; the CSV is evidence only for the commit named in its evidence column. Passing unit tests do not prove the deployment workflow; deployment is shown by real `python -m scripts.deploy_local` runs on a node, which the scripted demo and the measurement both use.

Compile commands require the Hardhat dependency and compiler download. Compiling is separate from functional test success. Python compile/import/startup checks do not prove consent enforcement, storage or blockchain connectivity.

Python unit tests live in tests/ and run with `python -m unittest discover -s tests` (standard library only, no node): 337 tests, all passing (test_measure 62, test_chain 57, test_records 55, test_demo 40, test_main 27, test_export_python_results 26, test_access 24, test_deploy 23, test_disclosure 17, test_tamper 6). test_access, test_tamper and the menu tests run against tests/fake_chain.py, which copies the agreed contract rules; test_demo and test_measure run the scripted demo and the measurement scenario against the same fake with the node calls mocked; test_chain and test_deploy mock web3 and the node; test_export_python_results covers the offline parts of the PY exporter. Without web3 (for example `.venv/bin/python -S -m unittest discover -s tests`, which hides the installed packages) the 86 tests that need it are skipped. They are evidence for the Python side only; on-chain rules are shown by the Solidity suites and the live runs.

The PY rows use the same header as the SOL rows. `python -m evaluation.export_python_results [--settings PATH] [--output PATH]` writes them to evaluation/results/test_results.csv (PY-01..PY-13) on a running node (chain 31337 only): it runs the unit tests with and without web3, the scripted demo, its own live checks on fresh contracts, the console's failure messages and a scan of every transaction for local values, and writes the CSV only when it could finish (it removes an old one otherwise). It replaces deployment_file, turns automine off and on again for the pending case and moves node time forward about two days, so redeploy (`python -m scripts.deploy_local --reset`) before using the menu again.

Required cases: registration and duplicates; clinic-only attestation; grant duration 0/1/194/195/365/366 days; wrong owner/requester/scope; revoked/exact-expiry denial; unavailable/mismatched record; granted and persistent denied events; first reward and repeat-grant prevention; unauthorized minter; no rewards during access.

Integration: `python -m integration.demo_workflow [--settings PATH]` uses real local transactions for deploy fresh contracts -> register -> attest (the guardian's own attempt is rejected with NotTrustedClinic) -> denied access -> grant/reward -> permitted school/doctor output -> tamper a copy while the doctor grant is active, denied (HASH_MISMATCH) -> revoke school, denied (REVOKED) -> regrant school for 1 day with no second reward, set the next block timestamp to expiresAt, denied (EXPIRED) -> reward balances and the six-event audit log. Every outcome is checked: the run ends with "demo passed" (exit 0) or "demo FAILED at step N: reason" (exit 1). The expiry step runs last because node time cannot go back. The console transcript is the evidence; the script does not save it. No real personal data is permitted.

Measure each contract's deployment gas and averages for comparable function calls. Separate first rewarded grants, unrewarded regrants, granted and denied access. Run scenarios with 1, 5 and 10 requester accounts (scenario_requester_account_indices in settings) in which every role acts: deployer (deploy, set minter), clinic (attest), guardian (register, grant, revoke), requesters (register, request); redeploy fresh contracts before each N and re-register and re-attest; report mean gas and time per operation and role. Record sample counts, gasUsed, send-to-receipt seconds and send-to-decoded-event seconds with a monotonic clock. Never invent gas results or describe local automining as public-network performance. All gas numbers use solc 0.8.28 with the optimiser on, 200 runs (hardhat.config.ts); state this under the gas table.

`python -m evaluation.measure [--settings PATH] [--output-dir DIR]` does this on a running node (chain 31337, automine on, as `npm run node` starts it) and writes evaluation/results/gas_results.csv, timing_results.csv, timing_summary.csv and ENVIRONMENT.md, only after all three runs succeeded. It deploys its own contracts for each N, leaves deployment.json alone and moves node time forward about one day per N. When citing the results:

- The timings are local automine numbers for transactions sent one at a time, about 5 ms each on the machine recorded in ENVIRONMENT.md. They show how cost and time grow with N, not throughput, latency or fees on a public chain.
- `npx hardhat test solidity --gas-stats` is only a cross-check. On Hardhat 3.18 its values equal receipt gasUsed (for example registerUser 45,430 and setMinterOnce 47,919), so they are not "execution gas" without the 21,000 base. Small gaps come from calldata: registerVaccination is 48,557 there and 48,545 in gas_results.csv, because the tests send a different hash and a zero byte costs 4 gas, any other byte 16.
- timing_results.csv has one row per operation, so its sample counts add up to each run's transactions (17, 61 and 116). The per-role and whole-run means over the same transactions are in timing_summary.csv; never add those rows to the per-operation ones.
- Deployer rows are send to verified deploy, not send to receipt: they are timed around deploy_local's verified steps, which also read the artifact file and read the runtime code (and trustedClinic() or minter()) back. View calls and calls that would revert are never mined, so they have no receipt and no row.

Each result file records the commit it was made at, marked "+ uncommitted changes" (solidity_test_results.csv: "+ uncommitted contracts/tests") when the files its results depend on differ from that commit: contracts/ and test/ for solidity_test_results.csv; contracts/, app/, scripts/, evaluation/measure.py, hardhat.config.ts and package.json for the gas and timing tables (the label is in ENVIRONMENT.md); app/, contracts/, integration/, scripts/, tests/, config/ and the exporter for test_results.csv. The current files were made before the changes were committed, so rerun `python -m evaluation.export_solidity_results`, `python -m evaluation.measure` and `python -m evaluation.export_python_results` once they are committed, and again after any contract change (after `npm run compile`).

CSV files in evaluation/templates contain headers only. Their missing result rows mean NOT MEASURED, not zero cost or successful tests.
