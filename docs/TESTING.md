# Validation and evidence

The project has three sources of evidence: the Solidity tests, the Python tests (offline unit tests and live checks on a node), and the gas and timing measurements. Each is regenerated by the commands below, run from the project root, and the results are in evaluation/results/. Setup and the other commands are in the [README](../README.md).

| Evidence | Command | Needs | Writes to evaluation/results/ |
| --- | --- | --- | --- |
| Solidity tests (SOL rows) | `python -m evaluation.export_solidity_results` | `npm ci`, no node | solidity_test_results.csv, solidity_test_run.log |
| Python unit tests | `python -m unittest discover -s tests` | Python 3.10 or newer, no node | nothing |
| Python live checks (PY rows) | `python -m evaluation.export_python_results [--settings PATH] [--output PATH]` | `npm run compile`, a running node (chain 31337) | test_results.csv |
| Gas and timing | `python -m evaluation.measure [--settings PATH] [--output-dir DIR]` | `npm run compile`, a running node (chain 31337, automine) | gas_results.csv, timing_results.csv, timing_summary.csv, ENVIRONMENT.md |

After any contract change, run `npm run compile` and then the three result commands again. evaluation/templates/ holds header-only copies of gas_results.csv, test_results.csv, timing_results.csv and timing_summary.csv. In any result file, a missing row or a blank cell means not run or not measured, never zero cost or a passing test.

## Solidity tests

`npm test` runs `npx hardhat test solidity` against the real contracts, needs no node, and prints `38 passing` with no failures. There are three suites under test/, named after their contracts:

| Suite | Test IDs | Tests |
| --- | --- | --- |
| test/IdentityRegistry.t.sol | SOL-IR-01..09 | 9 |
| test/ConsentManager.t.sol | SOL-CM-01..22 | 22 |
| test/ConsentRewardToken.t.sol | SOL-RT-01..07 | 7 |

Each test function carries its ID and expected behaviour in `@notice [SOL-XX-nn]`, its requirement in `@custom:requirement` and the reason it matters in `@dev Why it matters:`.

`python -m evaluation.export_solidity_results` runs the same command. It saves the raw console output to solidity_test_run.log and writes one row per test to solidity_test_results.csv, with columns test_id, requirement, why_critical, expected, actual, status and evidence. requirement, why_critical and expected come from the NatSpec, and actual and status come only from the run, so the CSV is also the catalogue of the tests.

- A test Hardhat lists as passing is "pass". A failing one is "fail", with Hardhat's error line.
- When a suite's setUp() fails, each of its tests is written as "fail" with actual "not run: setUp() failed: ...".
- A skipped test, or one missing from the output, gets no row, so a missing row means not run.
- The exporter refuses to write a CSV when a test function has no ID or an ID repeats, when Hardhat lists a test it cannot match to a function, or when its pass, fail and skip counts disagree with Hardhat's summary. If the run gives no usable results, it deletes the previous CSV and keeps the log.
- It exits 0 only when the CSV was written and every test passed.

What the suites cover:

| Case | Test IDs |
| --- | --- |
| Registration: one nonzero identity hash per wallet; duplicate and zero registrations rejected | SOL-IR-01, SOL-IR-02 |
| Attestation: only the trusted clinic, fixed at deployment; the guardian must be registered; evidence cannot be replaced | SOL-IR-03, SOL-IR-04, SOL-IR-07 |
| Grant duration: 0, 366 and 65535 days rejected; 1, 194, 195 and 365 accepted with the exact expiry | SOL-CM-02 |
| Wrong owner, requester or scope; unregistered parties; missing evidence | SOL-CM-04..07 |
| Revocation, and denial at the exact expiry second | SOL-CM-08, SOL-CM-09 |
| Changed or missing record (a wrong or zero observed hash) | SOL-CM-10 |
| Allowed and denied attempts both logged as events, with no revert | SOL-CM-06, SOL-CM-07, SOL-CM-11 |
| One reward per (owner, requester, scope): none for an active duplicate or a regrant after revoke or expiry; grant and mint are atomic | SOL-CM-01, SOL-CM-03, SOL-CM-12..15 |
| Minter set once, by the deployer; only ConsentManager mints, one unit, never to the zero address; the deployer has no later power | SOL-RT-01..04, SOL-RT-07 |
| No token moves during access; a balance never authorizes access; units cannot be transferred | SOL-CM-11, SOL-RT-05, SOL-RT-06 |
| Reads and events expose commitments only | SOL-IR-05 |
| What the Python code relies on: denial precedence, reason codes 0-7, revert order, lookups that never revert | SOL-CM-16, SOL-CM-17, SOL-CM-20, SOL-IR-06, SOL-IR-08 |
| Constructor checks, consent state in one storage slot, the demo story on-chain | SOL-CM-18, SOL-CM-21, SOL-CM-19 |
| Stated limitations: another wallet can register a copy of an identity hash; the tuple is the only reward limit | SOL-IR-09, SOL-CM-22 |

## Python tests

### Unit tests

`python -m unittest discover -s tests` uses the standard library's unittest and needs no node. All 337 tests pass:

| File | Tests | Runs against |
| --- | --- | --- |
| test_measure.py | 62 | the measurement scenario on the fake chain, deploy steps and web3-only helpers mocked |
| test_chain.py | 57 | the real app/chain.py with web3 and the node mocked; also checks that the fake keeps the real signatures |
| test_records.py | 55 | records, salts and commitments in temporary folders |
| test_demo.py | 40 | the scripted demo on the fake chain, with the few raw node calls and deploy_local mocked |
| test_main.py | 27 | the menu; its chain actions on the fake chain |
| test_export_python_results.py | 26 | the offline parts of the PY exporter |
| test_access.py | 24 | perform_access, the release rule in app/disclosure.py, and its school and doctor wrappers on the fake chain |
| test_deploy.py | 23 | scripts/deploy_local.py with web3 and the node mocked |
| test_disclosure.py | 17 | the school and doctor views and denial messages |
| test_tamper.py | 6 | the demo's tamper step on the fake chain |

Without web3, for example `.venv/bin/python -S -m unittest discover -s tests` (-S leaves out the venv's installed packages), the 86 tests that need web3 are skipped and the rest pass.

The fake chain, tests/fake_chain.py, is an in-memory stand-in for app/chain.py with the same signatures. It copies the contract rules in [CONTRACT_API.md](CONTRACT_API.md): the denial precedence, the named rejections and one reward per tuple. A unit test that passes against it shows that the Python code handles those rules, not that the contracts enforce them. The contract rules are shown by the Solidity tests and the live runs below. The unit tests also mock the deployment. Deployment is shown by the live runs: the demo and the PY exporter deploy with scripts/deploy_local.py, and the measurement uses its deploy steps.

### Live checks (PY rows)

`python -m evaluation.export_python_results [--settings PATH] [--output PATH]` runs on a node, on chain 31337 only because it moves node time. It writes the PY rows, PY-01..PY-13, to evaluation/results/test_results.csv (or `--output`), under the same header as the SOL rows. In one run it:

1. runs the unit tests with and without web3 (python -S);
2. runs the scripted demo as a subprocess, `python -m integration.demo_workflow --settings PATH`;
3. runs its own story on fresh contracts through the app code: register, attests from wrong accounts, attest, school and doctor requests, a tampered copy, a missing salt, a late recheck, unsupported scopes, a pending and an unreachable request, rewards and expiry;
4. makes the menu and the demo fail (node down, no deployment, rejected transactions, bad local files) and checks the text they print;
5. scans every transaction mined since step 2, the demo's included, for the record, identity and salt values: calldata, logs, and every storage write (debug_traceTransaction).

Two cases cannot happen by themselves under automine, so the run causes them, and its rows say so: a revokeConsent mined between the logged request and the final recheck, and a request sent with automine off and a 3-second receipt timeout.

| ID | Checks |
| --- | --- |
| PY-01 | The school gets measles status only; the doctor gets vaccine and date only |
| PY-02 | Denied, unavailable and pending responses release nothing |
| PY-03 | A tampered copy is denied with HASH_MISMATCH; the original still verifies |
| PY-04 | A missing salt sends the zero hash and is unavailable, not a clinical NO |
| PY-05 | A failed final recheck logs a second event |
| PY-06 | Only the trusted clinic can attest; guardian, school, doctor and deployer are rejected with NotTrustedClinic |
| PY-07 | On-chain storage and events hold only hashes and metadata |
| PY-08 | The guardian gets one unit per first grant of a (guardian, requester, scope) tuple |
| PY-09 | Attempts with unsupported scopes are logged and shown with the raw scope |
| PY-10 | Console failures print no exception text, paths or data |
| PY-11 | The scripted demo passes, with every local file under data_root |
| PY-12 | The unit tests all pass |
| PY-13 | Without web3 the unit tests have no failures and the web3 tests are skipped |

A row is "pass" only when every observation in it was as expected; an unexpected one is marked "(not as expected)" in actual. The CSV is written only when the run could finish; otherwise the previous CSV is removed. The exporter exits 0 only when every row passed. Its temporary files go under data_root and are deleted again. It replaces deployment_file twice (the demo's deploy, then its own), turns automine off and on again, and moves node time forward about two days, so run `python -m scripts.deploy_local --reset` before using the menu again.

### Scripted demo

`python -m integration.demo_workflow [--settings PATH]` runs the whole story with real local transactions and synthetic data, and checks every outcome. It ends with "demo passed" (exit 0) or "demo FAILED at step N: reason" (exit 1). Its console transcript is its evidence; the script saves nothing, and PY-11 records a passing run. [DEMO.md](DEMO.md) walks through it.

## Gas and timing measurements

`python -m evaluation.measure [--settings PATH] [--output-dir DIR]` runs on a node with chain 31337 and automine on, as `npm run node` starts it. For 1, 5 and 10 requesters (the first N accounts of scenario_requester_account_indices) it deploys fresh contracts and runs one scenario in which every role acts:

- deployer: the three deploys and setMinterOnce;
- clinic: registerVaccination;
- guardian: registerUser, grantConsent and revokeConsent;
- each requester: registerUser and requestAccess, scope MEASLES_STATUS only.

The order is: the guardian and each requester register; each requester is denied MISSING_EVIDENCE; the clinic attests; each requester is denied NO_CONSENT; the guardian grants each one (rewarded); each is allowed, then denied HASH_MISMATCH with one byte of the hash changed; the guardian revokes each, and each is denied REVOKED; the guardian regrants each for 1 day (no reward); node time moves to the latest expiry, and each is denied EXPIRED; the guardian regrants each after expiry (no reward). The four deployer transactions, the guardian's registration and the attest, plus 11 transactions per requester, make 17, 61 and 116 transactions for N = 1, 5 and 10. Every outcome is checked against the decoded event and the final reward balances. Identities and the record hash are synthetic hashes made by the script; no local file is read.

It records gasUsed from each successful receipt, and send-to-receipt and send-to-decoded-event seconds with a monotonic clock. It writes the files only after all three runs succeeded and the compiled contracts did not change during the run. It leaves deployment.json alone and moves node time forward about one day per N.

- gas_results.csv: one row per role, contract, function and scenario, pooled over the three runs, with sample count, total and average gasUsed, and notes. First rewarded grants, unrewarded regrants, allowed access and each denial reason are separate rows. All gas numbers use solc 0.8.28 with the optimiser on, 200 runs (hardhat.config.ts).
- timing_results.csv: for each N, one row per operation, with sample count, average gas, average receipt and event seconds, and failures. Its sample counts add up to each run's transactions (17, 61 and 116).
- timing_summary.csv: for each N, the per-role and whole-run means over the same transactions. Never add these rows to the per-operation ones.
- ENVIRONMENT.md: compiler, node, automine, machine and method. It is generated by the command.

When citing the results:

- The timings are local automine numbers for transactions sent one at a time, about 5 ms each on the machine recorded in ENVIRONMENT.md. They show how cost and time grow with N, not throughput, latency or fees on a public chain, and no gas is converted to money.
- Receipt seconds include web3's gas estimate and fee lookup, eth_sendTransaction (mining happens inside it) and eth_getTransactionReceipt.
- Deployer rows are send to verified deploy, not send to receipt. They are timed around deploy_local's verified steps, which also read the artifact file and read the runtime code (and trustedClinic() or minter()) back.
- View calls and calls that would revert are never mined, so they have no receipt and no row.
- `npx hardhat test solidity --gas-stats` is only a cross-check. On Hardhat 3.18 its values are receipt gasUsed, including the 21,000 base, so they are not "execution gas": registerUser 45,430 and setMinterOnce 47,919 are the same there and in gas_results.csv. Where the two differ, the cause is calldata: registerVaccination is 48,557 there and 48,545 in gas_results.csv, because the tests send a different hash, and a zero calldata byte costs 4 gas and any other byte 16.

## Which code a result belongs to

The evidence column of solidity_test_results.csv and test_results.csv, and the "Written by" line of ENVIRONMENT.md for the gas and timing tables, name the command, the short git commit and the UTC time. The commit is marked "+ uncommitted changes" ("+ uncommitted contracts/tests" in solidity_test_results.csv) when the files the results depend on differ from it:

- solidity_test_results.csv: contracts/ and test/;
- test_results.csv: app/, contracts/, integration/, scripts/, tests/, config/ and evaluation/export_python_results.py;
- gas and timing tables: contracts/, app/, scripts/, evaluation/measure.py, hardhat.config.ts and package.json.

Outside a git checkout the commit is recorded as unknown.
